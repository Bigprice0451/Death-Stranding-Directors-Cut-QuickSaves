# Restoring a private quicksave in Director's Cut

The playtest implementation submits a private world snapshot to the game's normal streaming and restore system when the matching world is already open. See [the load bridge](src/private_load.cpp) and [the native image checks](src/native_image.cpp). Its queue handoff, source lifetime and failure paths passed simulated-engine tests. An actual round trip in Director's Cut, cross-world boot, and exact cinematic resume still require separate evidence.

## Build and data format

These observations come from static inspection of the 64-bit Steam executable for Director's Cut, build `13300582`, SHA-256 `9d5306d7eb2f5d3135c63accc3e74b8f9b029f9d76112a6aae4a38fdbb4edd2b`. Addresses are hexadecimal offsets from the start of this executable in memory. An update can change all of them. Fields such as `+0x26` are byte offsets within a particular object.

The reader expects the game's decoded memory image. The first `0x200` bytes are its header. Byte `+0x24` gives the serialization version, byte `+0x25` holds flags, word `+0x26` identifies the game world, and the 32-bit length at `+0x1FC` covers the payload beginning at `+0x200`. Current native banks hold 12 MiB including the header. The archived `checkpoint.dat` in the earlier prototype contains a separate outer container. It cannot be passed directly to the reader. See [the capture investigation](NATIVE_CAPTURE.md) for the writer, digest and position measurement.

## How the engine chooses the source

1. The in-game load action reaches `0x2636990`, checks the native catalog via `0x26376E0`, then calls `0x362D750` with a category, slot number and reason. The title path at `0x2624A70` also checks that catalog. It reads the selected world from the slot metadata for boot. The examined calls carry no mod filename, user stream or independent request identifier.
2. `0x362D750` creates an engine-owned request. The request contains the phase at `+0x0C`, category at `+0x10`, slot at `+0x11`, buffer index at `+0x2C` and load reason at `+0x48`. In the ordinary non-retry path, `0x362D816` clears `0x200` bytes of the controller's retry buffer if it exists. This can occur before the checks that accept the request. Trying the function with an invented private slot can already change the player's retry state.
3. The controller's constructor at `0x3625350` allocates three 16-byte-aligned, 12 MiB buffers starting at `0x36254D0`. Their pointers live at controller offsets `+0xB8`, `+0xC0` and `+0xC8`. Normal disk reads at `0x3633C14` select the current first or second bank and advance the shared index. Slot `-2` with retry reason `5` selects the third bank at `0x3633BA4`. Other `-2` requests select the other rotating bank at `0x3633BD8`. A load request receives an index into these existing allocations. None of the inspected branches allocates a fourth buffer for the request.
4. The storage layer can register device names (`0x19FFF10`) and open a registered device (`0x1A00220`). The upstream load resolver at `0x3635630` constructs the native category prefix and slot number, checks the corresponding catalog, and passes the result down. Registering a private directory alone supplies no way for this request to select it. A numbered `manualsave` directory in the native category would also participate in vanilla catalog and rotation decisions.

Creating another full native controller adds itself to the global controller list and installs callbacks on the shared storage service. Its constructor and destructor call methods with the name `savegame.dat`. This Windows executable installs the virtual table at `0x3BA6488`, whose methods `+0x38`, `+0x40` and `+0x48` all return immediately at `0x18E9B10`. The load bridge verifies the effective `+0x40` target before submitting. On another build where this method retained the source, the lifetime requirements could change. The destructor at `0x3626A00` frees the three native allocations. The engine's `IsLoading` at `0x3668C50` queries the controller embedded in the active world at `+0x2A0`.

## How the playtest hands off one private request

1. Check the host executable, an active idle world, its native world ID, current game mode, the archive's SHA-256 and the native image's MD5 and fixed header fields. In particular the current build writes exactly `0x4C` bytes of activity metadata. The reader copies that length to a fixed-size local structure. Verify it before calling into the game.
2. Copy the image to mod-owned, page-aligned memory. Ask the native admission routine to construct one normal same-world memory load (`All`, `-2`, mode `2`, reason `1`). It receives an empty private queue with a null retry pointer. Its conditional header clear cannot affect the player's retry bytes. This short-lived structure exists only for admission. It has no callbacks, file device or native buffer allocations.
3. Use the game's move-insertion routine at `0x1906570` to move the actual request reference onto the active world's empty queue. The engine itself created the request and retained the current world. The insertion clears the source reference. Native removal at `0x362FC50` frees the now-empty temporary items allocation at `0x362FD22`. Subsequent gameplay can see the real load in the main queue.
4. On the regular game-update thread, point the selected first or second scratch entry at the private image for the two synchronous dispatches that select and open the reader. Restore the original pointer before returning to the game loop. The third native bank and the underlying bytes of both rotating banks are preserved. Ordinary save admission rejects a head request in phases 6 through 15 at `0x3630503`, and native load admission checks for existing loads at `0x362D93B`. If the request stalls before opening a reader, remove this request before restoring control. The game's own scheduler continues the asynchronous phases.
5. A private load cannot release its source just because its request vanishes. Wait for the same world, the end of the request, empty stream and reader pointers, and the cleared world-loading flag. The mod then frees the private image and attempts to measure the distance between Sam and the recorded position. A cutscene can have no current player entity. After half a second, return native completion with an unavailable position measurement. If the world disappears while the bytes may still be borrowed, retain them and stop further private restores for that run. An interrupted forced add-on unload can leave one 12 MiB allocation owned by the process until it exits.

The test in [private_load_simulation.hpp](tests/private_load_simulation.hpp) uses an in-process model of the native queue, scratch table and borrowed reader. It checks single ownership after the move, unchanged retry and rotating-bank bytes, synchronous source restoration, stalled-phase cleanup, different-world rejection and completed loads with and without a player entity. It cannot demonstrate real concurrent engine callbacks, game content, or quest-state behavior.

## Loading from the title or a different world

The title-menu path at `0x2624A70` resolves its selected native catalog entry. It obtains the map resource, records a category and slot in the campaign startup object and then opens the campaign. Later the bootstrap prepares storage and consumes the native slot before entering the same-world memory-load branch at `0x263F967`. No private image parameter was found in this chain.

The registered `StartGame` script at `0x3669400` requires a missing active world and launches a new campaign map. At `0x327B1EF` the menu uses this branch with `ds_world`. Its Continue branch takes a different path via the normal load menu. Automatically starting a fresh campaign and applying the snapshot later could run startup scripts or autosaves in between. This release requires the player to open an ordinary delivery first. Any delivery with the same native world ID can serve as the starting point. The mapping between the native world IDs and the game's named delivery regions has not been established.

## What happens after the bytes are selected

- In phase 8, disk loads compute a 16-byte digest over the declared payload and compare it with the header at `0x3633F1E`. A proposed private input needs a file-size and bounds check **before** a native reader consumes the length, plus the game's format and integrity checks. The memory-checkpoint branch normally trusts its engine-owned buffer.
- The phase dispatcher at `0x3633640` reaches phase 9 at `0x36340A7`. It checks the current map against the header's world and checks serialization compatibility. A different world requires a boot path that can select it. The dispatcher passes the bytes and length under the shared name `savegame.dat`, changes active-world flags and calls `0x3628110`.
- `0x3628110` constructs a memory stream over the payload, constructs the versioned reader and begins applying state to the current world and several managers. The stream constructor at `0x18FC750` retains the supplied start and end addresses. Source bytes must remain valid while the reader and later phases can use them.
- When needed, phase 11 waits on engine work and invokes more readers. Phase 14 passes the saved position or authored position override to streaming and waits for the area. Phase 15 calls `0x36346B0`, which checks outstanding work and registers callbacks carrying the controller pointer. On completion the dispatcher removes the request and clears the world loading flag. Calling only the phase 9 reader omits these steps. A timeout in an overlay cannot establish that the engine released the buffer.

## How precise is Sam's position?

The writer resolves the local player at `0x3629A27` and copies all three double-precision coordinates from the entity at `+0xC8`, `+0xD0` and `+0xD8`. With request flag `+0x19` cleared, it uses that current position. It writes rounded floats into the header at `+0x1E0`, `+0x1E4` and `+0x1E8` and writes all 24 original bytes through the native serializer at `0x3629B90`. The restore reader decodes the 24 bytes to controller `+0x18` at `0x36282C0`. Phase 14 uses these coordinates for streaming. Phase 15 submits them to a native streaming request at `0x36347FF`.

The save can also carry an authored position override. `0x2635DA0` reads its presence flag to world `+0x481` and, when present, its three doubles to `+0x488`. At `0x363423E`, the game can substitute those values for streaming. Entity creation, attachments and physics proceed through the engine's restore callbacks. These traces establish that the saved position reaches the game and that streaming can use an override. They do not establish the final position of a loaded actor in every situation.

After streaming, `position_difference` measures the Euclidean distance in world units between the three decoded doubles and the three doubles on Sam's live entity. `world_position_override` reports the saved flag. Comparing these measurements on foot, in a vehicle, and during a scripted move will show which situations preserve Sam's placement. A missing player gives `-1`. The mod makes no direct transform write. `Entity_ExportedSetWorldTransform` at `0x2361EA0` acts on a generic entity and there is no verified placement correction that also moves the character controller, vehicle, cargo and attached story actors coherently.

## Cutscenes

Decima's scripted sequences can fire quest facts, send messages, move actors and start child sequences. `SequenceComponent.GetSequenceCurrentFrameNumber` at `0x24D07C0` reads the current frame. `Sequence.Start` ultimately calls `0x24BBC90`, which resets the current frame, next frame and per-event state. The reflected `Sequence` and `SequenceComponent` interfaces examined here do not expose a saved playhead and history of completed events. The wakeup-dream save commands at `0x365C8F0` and `0x365C970` create authored save requests without passing an arbitrary scene or elapsed time.

The Bink movie player has a seek wrapper at `0x19CB270`. A decoder seek can move a playing video to a frame. It supplies no evidence about how to recreate the owning mission, audio timing, actors or once-only quest events. No individual story sequence was verified to resume at an arbitrary saved frame.

## In-game acceptance checks

- Confirm the private handoff in a live game during successful completion, cancellation and world changes. Record admission, native phases, the position measurement and both a later vanilla retry and an ordinary load. Test after restarting the game and opening the matching world again.
- In an isolated profile, save during a delivery, move a measured distance and change a visible state such as carried cargo. After a private load, compare Sam's position and orientation, the order objective, cargo condition and already-completed triggers with the captured values. Repeat after restarting the game and across different world maps. Check malformed and truncated files before any world mutation.
- In the same running session, exercise normal save, load and automatic checkpoints around the mod operation. Compare native save files and the retry point, allowing for changes from intentionally triggered vanilla operations. Verify the game's own retry after the private operation.
- Test scripted sequences and prerecorded videos separately. Capture two identifiable frames in each claimed scene, restart, resume, then complete the scene and next story objective. Record frame and audio continuity and verify that once-only quest events fire exactly once. A successful road load cannot establish cinematic coverage.
